## 1. 执行摘要

### 1.1 负责人结论

1. **当前系统值得有条件继续投入，但投入对象应是可信研究与交易基础设施，不是继续给现有 Dual 策略加规则。**
2. **当前不可以进入模拟盘，也不可以进入实盘。** 日/周高周期数据存在前视映射，Dual-layer 账本与真实持仓量纲不一致，手续费以外的执行成本、资金费率、保证金和爆仓未进入正式路径。
3. 三标的在当前失真条件下均为正收益，但都显著跑输对应买入持有。共同窗口内 BTC 的风险调整后表现最好；SOL 的表面年化最高，但收益主要集中在 2021 年和极少数大额交易；ETH 的后半段收益明显衰减。
4. 当前系统不是成熟的“多模块 Alpha”。三标的的 core_long 与 bear_core 合计贡献约 91%–95% 的表面净利润；大多数复杂战术规则只产生很小的净增量，且跨资产符号不稳定。
5. 当前年化不是 5 倍杠杆带来的：配置虽然写入 leverage=5，但 backtesting 引擎没有收到 margin 参数，实际是无保证金杠杆的 1× 上限模型。高收益主要来自高波动加密资产的趋势 Beta、早期牛市和少数尾部赢家；这不代表尾部风险已被正确建模。

### 1.3 保守因果护栏敏感性

为量化 HTF 问题，复现脚本另跑了不改业务源码的 causal_guard：日/周聚合 EMA 各后移一个完整高周期，并对三标的、日/周和多历史截面执行 138 次 future-truncation invariance 断言。周线因此可能被过度滞后，所以它是保守敏感性，不是最终修复版；它仍保留 Dual 账本、next-open、滑点、funding 和保证金缺陷。

### 1.4 当前最重要的三个问题

1. **因果性与数据语义不成立。** 日/周最终收盘被提前映射到同一周期内的 4H bar，尾部未完成 K 线和原缓存重复 bar 也会进入回测。
2. **组合、订单和实际持仓账本不成立。** Dual 宣称 core 与 tactical 共存，但 exclusive_orders=True；权益比例与币数量相除导致 26%–31% 的 1e-8 级幽灵交易，模块归因和资金占用失真。
3. **研究与执行约束不成立。** 无独立 OOS / Walk-forward，130 个配置字段加硬编码阈值；滑点、真实 funding、保证金、强平、部分成交、幂等和对账均未进入正式链路。

### 6.7 CLI 默认 HTF 控制

run_backtest.py 的 --strategy 字面默认值为 htf，但对 BTC、ETH、SOL 的控制组均在首根 next 确定性报 AttributeError：HTFStopStrategy 缺少 _USE_REGIME_GATE。复现脚本没有猜测性补丁，而是把三例写入 results/blocked_cases.json。故“优先使用当前默认”在当前提交上不可执行；选择 Dual 是为了运行 README 所称完整系统，不是对 HTF 与 Dual 的择优挑选。这个缺陷同时说明当前 CLI 默认路径没有被 CI 覆盖。

### 6.8 对十个结果问题的回答

1. **最适市场结构**：独立因果代理明确指向“持续上行的趋势市场”，由 core_long 获取 Beta；不是当前污染标签声称的 ranging。
2. **趋势/震荡/牛熊**：因果代理下三标趋势均正，BTC/ETH 震荡为负；熊市收益弱且 SOL 为负。波动维度不统一：BTC/ETH 低波动为正，SOL 低波动为负；SOL 高波动正收益受 2021 大趋势混杂。
3. **收益来源**：core_long + bear_core 占 91%–95%，方向以多头为主；BTC 较分散，ETH 主要 2020–21，SOL 主要 2021。
4. **少数交易贡献**：是，Top 10 分别贡献 63%、95%、131% 净利润。
5. **长期失效**：是，最大回撤持续 630、771、847 天；ETH/SOL 多年收益很低或为负。
6. **BTC 有效但迁移失效**：core 趋势 Beta 没有完全失效；sweep_short、breakout、crash 等模块迁移后符号翻转。
7. **泛化还是 BTC 拟合**：只能确认有限的趋势 Beta 可迁移；复杂战术模块和状态参数没有跨标的泛化证据。
8. **收益是否来自过高杠杆**：不是，因为 5× 未生效；但收益依赖高波动 Beta 和尾部赢家，且无爆仓模型，不能据此安全放大。
9. **收益是否值得复杂度**：目前不值得。几千行战术与组合规则只产生约 5%–9% 的表面增量，且 B&H 全面更高、账本失真。
10. **模块动作**：保留/重构 core、bear_core、简单 pullback；低权重研究 breakout 与 sweep_short；停用 sweep_long、core_add、meanrev、bulltrap 及死模块，详见第 9 节。

### 7.2 失败测试与复现状态

本地 unittest discovery 共运行 452 个测试，422 通过、30 error；30 个错误全部来自 tests/test_btc_risk_model.py，其测试通过给 backtesting Strategy.data 赋 FakeData，但当前 backtesting 0.6.5 的 data 为只读属性。平台 backtest / portfolio / risk / pipeline 相关 94 个测试通过。结论不是“业务逻辑只有 30 个问题”，而是依赖未锁、CI 不存在，当前提交无法在记录环境中做到全绿。

causal_guard_environment.json 记录了 guard 定义和 138 个截断不变性断言；results/causal_guard_summary.csv、causal_guard_annual_returns.csv 等保存了三标的结果。该护栏故意把完成高周期值推迟一个完整周期，不是建议直接上线的最终实现。最终修复应显式建模 event_ts、available_at、is_final 和正确日/周边界，再从原始快照重跑。

### 7.3 结果使用边界

- 本轮固定数据解决了“输入可以重跑”，没有修复策略的因果性和账本。
- 当前 Return、Sharpe、MDD 是当前缺陷代码的确定性输出，不是可投资业绩。
- 模块 PnL、交易数、胜率、盈亏比受 ghost trades 和强制换仓污染，置信等级低于权益曲线。
- 在 P0 修复前，不应继续调参，不应将 ETH/SOL 正收益解释为 Alpha 泛化，不应提高杠杆。

原始 overlap 计数为 BTC/ETH/SOL 140/158/107；剔除 1e-8 ghost 后仍有 16/19/6 个 material 交易生命周期重叠。它们不等价于同数量的真实并发仓位，却说明交易行不是独立下注样本。另有报告 bug：annual_returns.partial_year 只检查首尾月份，BTC/ETH 从 2020-01-05 才开始却被标成完整 2020 年；本报告因此把年度表作为近似日历归因，而非完整自然年审计。

原仓库 BTC cache 的独立重复敏感性保持其他条件不变并关闭 derivative bonus：含 14 个 4H、99 个 15m 重复时间戳时，总收益 302.82%、最大回撤 -18.66%、464 笔；keep-last 去重后为 306.90%、-18.66%、461 笔。重复在这次样本中低估约 4.08 个百分点并改变 3 笔交易，不能解释 HTF guard 的大幅下降，但仍会改变路径且违反确定性输入要求；详见 results/repo_cache_duplicate_sensitivity.json。

| core_long | 保留并重命名为趋势 Beta sleeve | 三标的最大收益源；必须单独对照 B&H、做波动率目标，不得包装成独立 Alpha |
| bear_core | 小权重保留、显著简化 | 三标的均正；probe/confirm/waterfall/V-reversal 规则过多，需压缩为简单熊趋势模型 |
| pullback_long | 降权并简化研究 | 三标的正贡献，但相对 core 较小；须证明对简单趋势的增量 |
| breakout | 保留简单基准 | 经济解释清楚，但交易过少且 SOL 为负 |
| sweep_short | 仅 BTC 低权重研究 | BTC 正、ETH/SOL 负；多空必须分离且做 funding/逼空压力 |
| dip_buy | 极小事件 overlay 研究 | 4–7 笔，成交假设最脆弱；需高分辨率事件回放 |
| sweep_long | 停用生产候选 | BTC/SOL 显著负，跨资产不稳定 |
| core_add | 停用并做路径消融 | 两标的负，可能只是在高位增加相关 Beta |
| meanrev | 停用，保留研究基准 | 几乎无交易且实现与 regime 声明冲突 |
| bulltrap / failed_bounce | 停用 | 极少或零交易，高自由度形态规则 |
| crash | 停用正式预算、保留事件研究 | BTC/SOL 正、ETH 负；样本少、盘中成交不可信 |
| derivative bonus | 立即停用 | 只有 BTC 约 66 天缓存，缺 point-in-time 全历史 |
| 手写 0–100 score | 从生产依赖移除 | 同一 EMA/MACD/RSI/ADX/ATR 信息被多个子分数重复计权 |
| legacy Dual portfolio / manual trailing | 替换 | 量纲、持仓共存和同 bar 路径错误无法用局部调参修复 |

“删除”先指从生产配置和风险预算中移除；代码保留一个研究周期做消融。不能把负 PnL 机械加回，因为删除模块会改变后续交易顺序与资金占用。

## 10. 提高年化收益的重点方向

目标排序是：先保证存活和几何复利，再增加独立 Alpha，最后才考虑复杂模型。以下“建议实施”都以 P0 修复为前提。

### 10.1 负责人分类

- **最可能形成真实 Alpha**：相对强弱轮动；多空分离后的简化熊趋势/拥挤信号；完整 point-in-time funding/OI/basis；简化趋势突破和回调。
- **主要改善复利效率而非 Alpha**：波动率目标、相关性预算、组合级风险、保证金和尾部约束。
- **当前只增加复杂度**：动态模块权重、参数自适应、端到端 ML、无 L2 数据的订单流、多周期条件继续堆叠。
- **应立即停止**：继续加人工例外；用杠杆掩盖 Alpha 不足；在 66 天 derivative 数据上调参；在 ghost/overlap 修复前优化胜率。
- **基础设施后再做**：funding/OI/basis、L2、ML、动态权重、自动 Alpha 开关、多资产实盘。

### 10.2 控制最大回撤下最可能提高 CAGR 的三个方向

1. 把 core_long 重构为波动率目标的趋势 Beta sleeve，并接入组合级风险预算。
2. 研究 BTC/ETH/SOL 相对强弱轮动，配合相关性上限和资产风险预算。
3. 多空完全分离，删除负贡献模块，重构 bear_core / sweep_short 的退出。

它们是研究优先级，不是收益承诺。任何“改善”必须以冻结 OOS 结果、成本后净收益和最大回撤门槛为准。

## 11. 目标系统架构

### 11.1 目标链路

Market Data → Data Validation → Feature → Regime → Signal Modules → Scoring / Selection → Portfolio Construction → Risk Engine（硬否决）→ Execution Engine → Exchange Adapter

Backtest、Paper、Live 只替换 Clock、MarketDataSource 和 ExecutionVenue；策略、组合与风险代码不得分叉。Monitoring 消费全链路事件，Research / Experiment Tracking 和 Configuration / Version Management 作为跨层控制面。

### 11.2 十六层职责摘要

| 层 | 核心输出 | 状态归属 | 当前最大差距 |
|---|---|---|---|
| 1 Market Data | 标准 MarketEvent | 原始追加存储、采集游标 | 无 event/available/final/revision 契约 |
| 2 Data Validation | ValidatedEvent / DQEvent | 规则版本、隔离记录 | 无独立门禁，缺失会静默变零 |
| 3 Feature | 有血缘 FeatureSnapshot | 特征定义、增量检查点 | HTF 前视，快照未绑定数据 hash |
| 4 Regime | 概率化 RegimeState | 模型/滤波状态 | 状态散落、无 OOS 校准 |
| 5 Signal Module | SignalIntent | 原则无状态或可重放状态 | 策略直接 buy/sell/close |
| 6 Scoring / Selection | SelectedSignal / 拒绝原因 | 校准和审计日志 | 重复计权、冲突顺序不清 |
| 7 Portfolio | TargetPortfolio | 目标与预算 | submit 时预创建实际 position |
| 8 Risk | Approved/Rejected Intent | 限额、高水位、Kill Switch | 正式路径可绕过、无组合保证金 |
| 9 Execution | Order/Fill/ExecutionReport | FSM、outbox、fill ledger | 不存在生产级状态机和幂等 |
| 10 Exchange Adapter | 标准订单/账户事件 | 连接与限频游标 | 当前主要只读行情 |
| 11 Backtest | 冻结账本和指标 | 单 run 不可变归档 | legacy 与 generic 双引擎、成交不真实 |
| 12 Paper | 虚拟订单/成交/账户 | 独立持久化 paper ledger | 未实现 |
| 13 Live | 实盘编排与恢复 | checkpoint、租约、审批 | 未实现恢复、对账与 runbook |
| 14 Monitoring | Alert / Incident / 日报 | 指标、日志、事故记录 | 缺结构化可观测性 |
| 15 Research Tracking | 不可变 ExperimentRun | 试验族、晋级记录 | 无 manifest、WF、多试验治理 |
| 16 Config / Version | ResolvedConfigBundle | 版本、审批、secret 引用 | 配置散落、依赖未锁、BTC 硬编码 |

### 11.3 必须满足的不变量

- 策略只发 SignalIntent，不直接发交易所订单。
- Portfolio 输出目标头寸，不假设成交；实际持仓只能由 FillEvent 改变。
- RiskEngine 有强制否决、缩量和 Kill Switch 权限。
- Execution 处理部分成交、撤单、拒单、重试、重复回报和稳定 clientOrderId。
- 重启后从持久化 event/fill ledger 恢复，再与交易所对账；对账完成前禁止新增风险。
- 每次回测可追溯到 commit、dirty state、resolved config、data hash、lock、seed、cost model、engine version 和 ledger hash。

完整的每层输入、输出、依赖、避免耦合与差距见 [架构路线图附录](./architecture_roadmap_appendix.md)。

## 14. 最终管理层结论

### 14.1 是否值得继续投入

**有条件值得。** 值得投入的是数据因果、统一账本、风险/执行内核、可复现研究和 core 趋势假设；不值得继续投入的是在当前 Dual legacy 路径上堆规则和追求更高历史收益。

### 14.2 是否可以进入模拟盘

**不可以。** Paper Trading 不是“无资金所以无风险”；当前信号因果、持仓状态和订单语义不成立，进入模拟盘只会产生无法解释的回测—模拟偏差。完成阶段 0、1、2 的晋级门槛后，才进入阶段 3。

### 14.3 是否可以进入实盘

**明确不可以。** 当前没有生产执行状态机、幂等、重启恢复、账户对账、真实保证金/强平、监控与 Kill Switch 闭环。

### 14.4 三个核心管理判断

1. 三标的正收益不是系统优秀的充分证据；它们都跑输 B&H，且主要是趋势 Beta。
2. 当前复杂度没有得到相称 Alpha：core + bear_core 占绝大部分利润，多个战术模块跨资产翻负。
3. 最优的“提高年化”路径不是加杠杆，而是先消除负 Alpha 和复利拖累，再做跨资产选择与风险预算。

### 14.5 最终明确答案

- **当前系统是否值得继续投入**：是，但仅限 P0/P1 基础设施和简化研究；暂停规则堆叠。
- **是否可以进入模拟盘**：否。
- **是否可以进入实盘**：否。
- **最重要三个问题**：HTF/数据因果；组合与 fill ledger；真实成本/账户风险加 OOS 研究治理。
- **未来 30 天五项工作**：冻结复现；修因果/DQ；重建账本；接入成本/保证金/强平；重跑三币并冻结 OOS 协议。
- **控制最大回撤下最可能提高年化的三个方向**：波动率目标的 core sleeve；三币相对强弱与相关性预算；多空分离并删除负贡献模块。

在阶段 0 修复后，所有 BTC、ETH、SOL 结果必须从固定原始数据重新生成。旧结果仅保留为“缺陷复现基线”，不得与修复后结果拼接、续写或用于宣传。
