## 1. 附录目的与结论边界

本附录聚焦工程架构、回测可信度基础设施和从研究到实盘的演进路径，不重复主报告中的绩效数字，也不补造任何尚未完成或无法复现的回测结果。文中的“已确认”来自当前代码、配置和测试行为；仅凭静态代码无法判定的事项均列为“待验证”。

当前系统已经具备策略研究、特征计算、风险与组合抽象以及事件驱动回测的若干组件，但正式 BTC 回测入口仍主要依赖 quant_btc 中的单体策略，并在策略内部直接调用买卖和清仓接口。quant_platform 中较通用的信号、组合和风险组件尚未成为正式回测、模拟盘和实盘共用的唯一决策链路。仓库也没有完整的模拟执行场所、实盘订单状态机、持久化成交账本、重启恢复和账户对账闭环。

因此，目标不是继续在现有单体策略上堆叠规则，而是先建立一条可因果验证、可复现、可审计、可恢复的统一交易链路。阶段 0 完成前，任何收益提升都只能视为研究线索；阶段 3 完成前不得进入真实资金实盘。

## 2. 目标架构的控制原则

目标系统采用一套决策内核、三种运行场所：

Market Data → Data Validation → Feature → Regime → Signal Module → Signal Scoring and Selection → Portfolio Construction → Risk Engine → Execution Engine → Exchange Adapter

回测、模拟盘和实盘只能替换 Clock、MarketDataSource 和 ExecutionVenue，不得复制或分叉策略、组合构建和风险逻辑。

必须长期成立的工程不变量如下：

1. 策略模块只产生带时间戳、有效期、方向、强度、理由和版本的 SignalIntent，不得直接调用交易所、买卖、撤单或清仓接口。
2. 组合构建输出目标头寸或目标风险，而不是实际订单；风险引擎是执行前的强制门禁，有权否决、缩量、延迟或触发全局 Kill Switch。
3. 目标头寸、预留风险、未成交订单和实际持仓必须分离。实际持仓只能由 FillEvent 改变，提交订单不能预创建实际持仓。
4. 每个订单必须具有稳定的客户端幂等键和完整状态机；部分成交、撤单、拒单、超时、重试和重复回报都必须幂等。
5. 交易所账户快照是外部事实源，内部状态通过持久化事件账本重放并与交易所周期性对账；重启后先恢复和对账，未完成前禁止新增风险。
6. 所有行情和特征都必须遵守 point-in-time 语义。信号时刻只能读取当时已经完成且可获得的数据，高周期特征必须使用已经完成的高周期 K 线。
7. 每次研究和回测必须保存代码提交、工作区状态、解析后配置、数据清单与校验和、依赖锁、随机种子、成本模型、引擎版本和结果账本哈希。
8. 同一输入、同一环境和同一配置应产生字节级一致或经过定义的数值容差一致结果；任何无法复现的结果不得进入决策材料。
9. 对同一根 K 线同时触发止损和止盈等不可观察的盘中路径，回测必须采用明确、保守且可配置的成交规则，并在报告中披露。
10. 研究控制面、监控控制面与交易数据面必须隔离；查看页面或 GET 请求不得隐式触发高成本回测、下单或状态变更。

## 4. 统一回测、模拟盘和实盘的实现契约

### 4.1 唯一决策服务

应把 FeatureSnapshot、RegimeState、SignalIntent、TargetPortfolio、RiskDecision 定义为稳定领域契约，并由一个 DecisionService 串联。BacktestEngine、PaperTradingEngine 和 LiveTradingEngine 都调用同一 DecisionService，禁止分别继承或复制策略类。

运行场所只提供三个可替换接口：

- Clock：历史事件时钟、实时事件时钟。
- MarketDataSource：冻结快照、实时订阅。
- ExecutionVenue：SimulatedVenue、PaperVenue、ExchangeVenue。

除这三个接口及运行编排外，信号、选择、组合和风险代码应完全一致。

### 4.2 因果和成交语义

- 每个行情事件同时记录 event_ts、available_ts 和 is_final。策略只能消费 available_ts 不晚于当前决策时刻且 is_final 为真的数据。
- 低周期上使用日线或周线特征时，只能映射最近一根已经完成的高周期 K 线。必须用单元测试证明在高周期结束前修改其未来价格不会改变当前信号。
- 默认成交模型应为“信号在 K 线完成后产生，最早在下一可交易事件成交”；若策略声明收盘竞价或盘中触发，必须使用相应可观察数据和延迟模型。
- 同根 K 线同时碰到止损与止盈时，应使用保守优先、次级时间周期回放或路径随机化压力测试，不得默认选择有利路径。
- 手续费、滑点、资金费率、借贷成本、保证金和爆仓都应是独立版本化模型。资金费率必须按结算时间、持仓方向和实际名义价值结算，数据缺失不得静默视为零。

### 4.3 状态、幂等和恢复

- SignalIntent、RiskDecision、OrderCommand、OrderEvent 和 FillEvent 都携带 correlation_id、causation_id、schema_version 和幂等键。
- ExecutionEngine 使用持久化 outbox：业务状态和待发送命令原子落库，发送失败可重试但不产生第二个经济订单。
- 订单状态至少覆盖 CREATED、SUBMITTING、SUBMITTED、PARTIALLY_FILLED、FILLED、CANCEL_PENDING、CANCELED、REJECTED、EXPIRED 和 UNKNOWN。
- FillEvent 是实际持仓和现金账本的唯一内部变更来源；交易所账户快照用于对账，不直接覆盖未解释差异。
- 重启顺序固定为：加载检查点 → 重放未完成事件 → 查询交易所开放订单、成交、账户和持仓 → 生成差异 → 人工或规则化处置 → 解除风险冻结。

### 4.4 可复现和可追溯

每次回测、模拟和实盘部署均生成 RunManifest，最低包含：

- Git commit、工作区是否脏以及源码包哈希；
- 完整解析后配置及配置哈希；
- 数据文件清单、时间范围、行数、数据校验和、来源和修订版本；
- Python、操作系统、依赖锁和容器镜像摘要；
- 特征、市场状态、成本、撮合和风险模型版本；
- 随机种子、时区、浮点/数值容差；
- 订单、成交、交易和权益账本哈希；
- 报告生成器版本和生成时间。

同一 manifest 在隔离环境连续运行三次，应产生相同账本哈希。若存在并行或随机模拟，必须固定种子并声明允许的数值容差。

## 5. 工程缺陷优先级

优先级定义：

- P0：会使回测结论不可信，或会在模拟/实盘造成错误仓位、绕过风险、重复订单和不可恢复状态；未关闭前禁止进入下一运行阶段。
- P1：显著影响研究质量、风险刻画和长期运维；阶段 1 或模拟盘前必须关闭。
- P2：影响维护成本、扩展效率和操作体验；可在 P0/P1 稳定后按收益排序处理。

## 8. 30 天周拆解

### 第 1 周：冻结事实与建立红线

目标：让团队对“正在运行什么、用的是什么数据、哪些测试已失败”形成唯一事实版本。

- 建立当前代码、配置、依赖、数据文件和结果产物清单。
- 固定 Python 与依赖锁；在全新环境复现全量测试失败基线。
- 为 BTC、ETH、SOL 生成数据快照清单、校验和、时区、重复、断档和完成 K 线报告。
- 定义 RunManifest、MarketEvent、SignalIntent、RiskDecision、OrderEvent 和 FillEvent 最小 schema。
- 形成 Backtest Semantics ADR，明确决策时刻、成交时刻、止盈止损冲突、资金费率和滑点假设。
- 给现有 P0 指定 owner、截止日和独立复核人。

周验收：依赖锁和 CI 骨架可运行；数据质量报告可生成；每个现有结果能明确标注“可复现”或“不可复现”，不能保持模糊状态。

### 第 2 周：修复回测因果与状态正确性

目标：消除最可能扭曲绩效和制造幽灵仓位的机制。

- 修复高周期完成 K 线映射，并增加未来值扰动不影响当前信号的测试。
- 将默认撮合改为下一可交易事件，增加延迟和缺口场景。
- 明确同根 K 线止损/止盈路径，默认采用保守规则并输出歧义计数。
- 重做资金费率、手续费和滑点的逐笔现金流账本。
- 拆分 TargetPosition、ReservedExposure、OpenOrder 和 FilledPosition；撤单、拒单、部分成交和重复事件全部覆盖。
- 禁止衍生数据异常静默回零；关键字段缺失时运行 fail-closed。

周验收：因果、资金费率、成本、拒单、撤单、部分成交和幂等测试全部通过；修复前后差异可以由账本解释。

### 第 3 周：统一决策链路、风险门禁与配置

目标：建立正式回测未来可直接复用到模拟盘的唯一核心。

- 从代表性模块开始，把策略输出改为 SignalIntent，不再直接执行订单。
- 固定链路顺序：特征 → 状态 → 信号 → 选择 → 组合 → 风险 → 执行。
- 风险引擎改为不可绕过的硬门禁；补齐高水位、日周回撤、挂单预留和基础保证金字段。
- 统一 ResolvedConfig，移除 BTC/USDT、默认交易所、市场类型和杠杆的策略硬编码。
- 让正式 CLI 与预览调用同一 DecisionService；旧路径只保留受控回归对照。
- 为策略禁止依赖订单/交易所接口增加架构测试。

周验收：代表性端到端场景中，每笔订单都有唯一 SignalIntent、TargetPortfolio 和 RiskDecision；风险拒绝后订单数为零；配置扫描无标的硬编码。

### 第 4 周：复现、研究基线和 Go/No-Go

目标：用完整证据判断是否真正完成阶段 0，而不是按时间表自动宣布完成。

- 修复剩余测试错误并使全量 CI 通过。
- 在冻结数据上运行买入持有、零信号和当前候选基线；保存完整 manifest 与账本。
- 同一 manifest 连续运行三次并比较账本哈希。
- 生成统一 BTC、ETH、SOL 数据口径和假设表，但不对缺失或不可比区间补造结果。
- 预注册 IS、验证、OOS、Walk-forward、成本压力、Monte Carlo 和模块消融协议。
- 完成 P0 独立复核、风险签字和阶段 0 Go/No-Go 会议。

周验收：全量测试零错误；复现哈希一致；P0 每项有关闭证据。任何一项未满足则结论为 No-Go，并进入修复延期，不得转入策略调参或模拟盘。

### 第 29–30 天：管理层交付与下一阶段排期

- 归档代码、数据、配置、依赖、测试、账本、报告和审批证据。
- 输出阶段 0 差异报告：哪些历史结果仍有效、哪些需废止、变化来自何种语义修复。
- 明确阶段 1 的实验预算、封存 OOS、候选数量和停止规则。
- 发布阶段 1 的 owner、里程碑、评审日和资源需求。

最终交付不是一份“更漂亮的回测图”，而是一条任何独立人员都能重建、审计并拒绝不合格结果的研究生产线。

## 9. 管理层决策门槛

- 继续投入：建议继续，但资金首先投向可信度、统一引擎和风险执行基础设施，而不是新增规则或提高杠杆。
- 进入模拟盘：当前不具备条件。至少需要阶段 0、阶段 1、阶段 2 的晋级门槛全部通过，并完成持久化 PaperVenue 和订单状态机。
- 进入实盘：当前明确不具备条件。只有阶段 3 连续运行、故障演练、对账和 Kill Switch 验收全部通过后，才可申请单交易所、单标的、极低风险的小资金实盘。
- 任何阶段的盈利都不能替代工程门槛；任何无法复现、无法对账或风险可被绕过的结果都不得作为扩资依据。
